흥미로운 건 capability 선언의 엄격도가 거꾸로다. _Carla0916Client.capabilities()는 ("FIXED_STEP","GT_OBJECTS")를 하드코딩해 반환하는 정적 선언인 반면, metadrive_probe.py는 7개 capability를 실제로 동적 프로빙한다(§4) — "실행까지 완성된" CARLA 쪽이 오히려 capability 검증은 더 허술하고, "실행이 비어있는" MetaDrive 쪽이 capability 검증만은 더 엄격하다.

03

approve / native tick / terminal — exactly-once의 원리

여기서 다루는 TickApprove/CommandSetReady/FrozenInputSet/StepComplete/FrameAbort는 전부 avva_contracts/frame.py(157줄, 10개 dataclass) 소속이다 — 로직 없이 타입만 정의하는 계약 파일(§2의 backend.py와 같은 성격).

① Approve 재요청은 새 판단이 아니라 과거 답의 재확인

승인은 한 번 내려지면 내용을 저장해둔다. 같은 frame에 또 승인 요청이 오면 새로 판단하지 않고 "저장된 요청과 내용이 완전히 같은가"만 본다. 같으면 저장된 답을 그대로 반환(재승인 아님, 재확인), 조금이라도 다르면 재요청이 아니라 모순으로 보고 거부한다.

원리: 두 번째 호출을 막는 게 아니라 아무 효과도 없게 만든다 — 멱등성을 락이 아니라 메모이제이션으로 구현한다. 네트워크 중복 전송을 걱정할 필요가 없어진다.

구현 CoreFrameCoordinator.on_ready() (frame_coordinator.py)

② Native tick 결과를 몰라도 기회는 이미 썼다고 친다

tick은 되돌릴 수 없는 실제 side-effect라서, "성공 확인 후 재시도 여부 결정"은 위험하다. 타임아웃/예외가 나면 "진짜 안 됐는지, 됐는데 응답만 안 왔는지" 알 방법이 없기 때문이다.

원리: native 호출을 시도하기도 전에 "이 frame의 tick 기회는 이미 소비됐다"고 먼저 기록한다. 성공/실패/불명 무엇이든 상관없이 시도가 시작된 순간 재시도 가능성 자체를 차단하는 비관적 토큰 소비(pessimistic consumption)다. 결과를 알 수 없는 상황에서 안전한 쪽(재시도 금지)으로 미리 결정해버리는 방식이다.

여기에 사후 검증이 하나 더 붙는다: tick 후 "시뮬레이터 자체의 프레임 카운터가 정확히 1만큼 늘었는가"를 확인한다 — 토큰 체크로는 못 잡는 종류(다른 경로로 native tick이 몰래 두 번 불린 경우)를 잡는 독립적 2차 방어다.

이 사후검증은 코드 로직뿐 아니라 wire 계약 자체에 필드로 박혀 있다 — StepComplete는 native_frame_id(exactly-one step 검증용, 필드 설명에 명시)와 tick_confirmed: bool을, FrameAbort는 native_step_started/native_frame_before/native_frame_after를 각각 필수 필드로 갖는다 — Core가 메시지만 보고도 "tick이 실제로 몇 번 실행됐는지"를 재검증할 수 있게 강제된 구조다.

그리고 "알 수 없는 결과"가 한 번이라도 나면 그 frame만 막는 게 아니라 세션(런) 전체의 이후 native 호출을 다 막는다 — 한 번이라도 불확실한 상태가 생기면 그 시뮬레이터 인스턴스 자체를 더는 신뢰하지 않는다는 뜻이다.

구현 토큰 등록 SimulatorFrameExecutor.execute() (frame_executor.py) · 단조 체크·사후 검증·세션 봉인 CarlaBackend.execute_frame() (backends/carla.py)

③ Terminal 결말은 한 번 나면 고정, 양쪽이 각자 기억한다

frame이 commit이든 abort든 결말이 확정되면 그 결말 자체를 저장한다. 같은 frame의 결말을 다시 요청/통지받으면 ①과 같은 원리로 "새로 계산 않고 저장된 결말을 재확인"한다.

여기엔 하나가 더 붙는다: 이 확인을 결말을 결정하는 쪽과 통지받는 쪽 양쪽이 각자 독립적으로 한다. 둘 사이의 통신 채널은 메시지를 잃거나 중복시킬 수 있다고 가정해야 하므로, "나는 정확히 한 번만 보냈다"만으론 부족하고 "같은 내용을 몇 번 받아도 정확히 한 번만 처리한다"를 양쪽 다 각자 지켜야 전체가 exactly-once가 된다. publish(외부 통지) 자체의 재시도도 별도로 막아서 내부 상태 안전이 외부 중복 통지로 무너지지 않게 한다.

구현 내부 상태 PendingFrameRegistry.mark_terminal() · 결과 확정/publish 방어 SnapshotCommitPublisher.finalize()/_publish_terminal() · Core 쪽 독립 dedupe on_step_complete()/on_frame_abort()

세 원리를 묶는 것 "먼저 쓰고 나중에 확인" + "혼자만 만진다"

②③에서 반복되는 핵심은 "확정 먼저, 실행은 그다음" — 일반적 직관("해보고 성공하면 기록")과 반대로 뒤집혀 있다. 되돌릴 수 없는 side-effect를 다룰 때 나오는 표준 안전장치 패턴이다.

그리고 이 "체크했다가 표시한다"는 동작이 안전하려면 그 순간 딱 하나의 실행 흐름만 그 상태를 만질 수 있어야 한다 — 두 스레드가 동시에 "아직 안 썼네"를 통과하면 원리가 무너진다. 그래서 모든 컴포넌트가 "자신을 최초로 건드린 실행 흐름 하나에만 묶이고 다른 흐름이 건드리면 거부한다"는 규칙(_FirstOperationThreadOwner 패턴)을 공유한다 — 이게 위 세 exactly-once 보장이 실제로 성립하기 위한 전제 조건이다.

근거: 백엔드가 부분 실패 상태를 만들 수 없게 원천 차단.

단점: 이미 동작하는 3개 백엔드를 전부 다시 써야 함 — 지금 갈아엎을 비용이 큼.

→ A 유지. exactly-once는 이미 gate.py의 3중 방어(§3)가 커버하고 있어, 인터페이스까지 바꿔서 같은 보장을 중복으로 넣을 이유가 없다. 이미 검증된 3개 백엔드를 갈아엎는 비용이 이득보다 크다.

05

Input / Actuation — 기존 설계와 어떻게 다른가

command freeze · input digest · actuation realization · actor lifecycle 네 갈래.

command freeze 몇 개의 독립 입구를 열어두는가

InputGate엔 ingest_ego(), ingest_traffic() 두 개의 공개 수신 메서드만 있고 ingest_lifecycle() 같은 건 없다. avva-platform도 실제 메시지 레벨에선 own과 똑같이 ego+npc 2개만 진짜 입력이다. lifecycle은 freeze() 내부에서 _resolve_lifecycle()이 주입된 lifecycle_provider 콜백을 부르거나(없으면 빈 배치 생성) 하는 방식으로 내부 해석되지, 메시지로 "도착"하는 세 번째 입력이 아니다. 코드 주석 자체가 이를 인정한다 — "Public API에 누락된 lifecycle 운송 경로를 composition boundary에서 명시적으로 주입한다": 공식 계약(Public API)엔 lifecycle 입력 채널이 없고, lifecycle_provider는 그 구멍을 메우는 장치다.

own은 lifecycle_intents를 NpcControlBatch 안의 정식 필드로 넣어서 traffic 메시지와 함께 처음부터 통합해 보낸다.

원리 차이 — avva-platform은 InputGate 레벨에서 "lifecycle을 정식 채널 없이 별도 개념으로 취급하고 provider injection으로 땜빵"하고, own은 "lifecycle을 애초에 traffic 메시지의 일부로 설계해 정식 통합"한다.

정정(재검증 결과) — 위 서술은 InputGate 기준으로는 맞지만 시스템 전체로 보면 절반만 맞다. avva_traffic_ros/traffic_node.py의 worker 결과는 (NpcControlBatch, LifecycleIntentBatch, TrafficStepReport, TrafficRuntimeStatus) 4-tuple이고, 실제로 publish_lifecycle_intents()를 호출해 lifecycle_intents 전용 ROS 토픽을 발행한다(테스트가 아니라 실제 worker 경로). avva_sim_ros/simulator_node.py에도 이미 on_lifecycle_intents() 구독 콜백이 있다. 문제는 채널 부재가 아니라, 이 콜백이 받은 값을 InputGate.lifecycle_provider로 연결해줄 handler 구현이 repo 어디에도 없다는 것(테스트 fixture조차 on_lifecycle_intents를 구현 안 함) — Traffic은 발행하는데 Sim 쪽에서 아무도 안 받는 상태다. avva는 lifecycle을 별도 채널로 분리하는 설계까지는 이미 했고, own이 실제로 앞선 지점은 그 설계를 domain 계층까지 끝까지 연결했다는 실행 완성도 쪽이다.

구현 InputGate.freeze()/_resolve_lifecycle() · SimulationLayer._try_ready() (gate.py) · publish_lifecycle_intents() (avva_traffic_ros/traffic_node.py, 신규) · on_lifecycle_intents() (avva_sim_ros/simulator_node.py, handler 없음)

lifecycle을 own처럼 NpcControlBatch 안에 묶을지, avva처럼 별도 채널로 뺄지는 실제로 갈리는 선택이다.

A. own 유지 — NpcControlBatch에 통합권장

지금처럼 traffic 메시지 안에 lifecycle_intents 포함.

근거: 이미 동작, 메시지 수 적음 — avva가 겪은 "공식 채널이 없어 provider injection으로 땜빵"하는 문제 자체가 own 설계엔 없다.

단점: NPC 생성/삭제 타이밍이 traffic 제어 발행 주기에 묶인다.

B. avva처럼 별도 lifecycle 채널 신설

traffic 제어와 생명주기를 메시지 레벨에서 분리.

근거: 두 관심사가 독립적으로 진화 가능해짐.

단점: avva는 채널 분리 설계는 해뒀지만(Traffic→lifecycle_intents 토픽→Sim 구독) Sim 쪽 수신 handler가 없어 domain 계층까지 끝까지 연결하지 못했다 — 그대로 참고할 "완성 사례"는 아니다.

→ A 유지. avva는 채널 분리까지는 해냈지만 handler 연결을 안 끝냈다 — "avva가 같은 문제를 못 풀었다"가 아니라 "avva는 다른 방향을 골랐고 아직 안 끝냈다"가 더 정확하지만, own의 통합 방식이 지금 당장은 더 완성도 높은 선택이라는 결론 자체는 그대로 유지된다.

input digest 실제로 확인한 결과, 방식 자체가 다름

avva_contracts/algorithm.py의 stable_digest()를 직접 확인했다:

dataclass → 필드명 기준 dict로 재귀 변환 → JSON 직렬화(sort_keys=True) → SHA-256

JSON 기반이고 필드 순서는 dict key를 알파벳순 정렬해서 결정된다. numpy 배열은 {dtype, shape, values(list)}로 풀어서 JSON에 태운다.

own(hashing.py)은 CanonicalWriter로 고정폭 바이너리 인코딩을 한다 — u8/u16/u32/f64/bool8/uuid128/hash256 등 타입별 정확한 바이트 수, 필드 순서는 IDL 스펙에 정의된 순서 그대로(알파벳 아님), masked-off 필드는 인코딩에서 제외하는 규칙까지 명시적으로 문서화(§4.6, §6.6)돼 있다.

원리 차이: avva-platform은 "필드 이름을 정렬 기준으로 쓰는 구조적 해시", own은 "스펙에 못 박힌 바이트 순서의 이진 해시"다. avva-platform 방식은 필드 이름이 바뀌면(의미가 같아도) dict key가 바뀌어 digest가 달라진다 — own 방식은 필드 이름을 아예 해시에 안 넣고 값/순서만 고정폭으로 인코딩하므로 이름 변경엔 영향받지 않는다(값의 의미가 실제로 바뀌면 둘 다 당연히 바뀐다). 대신 own은 인코더를 손으로 유지보수해야 하고, 필드 추가 시 인코더를 안 고치면 조용히 스펙과 어긋날 위험이 있다(capability_canonical_bytes()의 assert len(fields) == 11 같은 필드 수 체크로 방어). stable_digest()는 이론적으로 비표준 JSON(NaN/Infinity 리터럴)을 만들 수 있는 구조이지만, 실제 digest 대상 타입(TickApprove, FrozenInputSet 등)엔 float 필드가 거의 없고 ActuationRealizer.realize()처럼 수치가 들어가는 경로는 해시 계산 전에 np.isfinite() 체크를 먼저 거친다 — 이 구조적 여지가 실제로 뚫리는 호출 경로가 있는지는 확인하지 못했다.

구현 stable_digest()/_canonical() (algorithm.py) · CanonicalWriter 기반 *_hash() 함수들 (hashing.py)

own의 CanonicalWriter 방식이 이미 팀이 정한 표준(avva_hash_v1 공지: "canonical byte encoding 규칙은 common encoder가 담당, Layer는 실제 값만 구성")과 일치한다.이미 결정됨

→ own 유지, 검토 불필요. avva-platform의 JSON 방식으로 바꿀 이유가 없다 — own 쪽이 이미 팀 표준을 따르고 있고 필드 이름 변경에도 안전한 더 엄격한 방식이다.

actuation realization 제어 변환을 어디서 계산하는가

CanonicalControlTarget(avva_contracts/control.py, 25줄)은 steering_tire_angle_rad/steering_rate_radps(횡방향)와 velocity_mps/acceleration_mps2(종방향) 필드를 갖는다 — 아래 P vs PID 비교가 정확히 이 필드들을 가리킨다. 같은 타입에 jerk_mps3 필드도 있지만 ActuationRealizer.realize()는 이 값을 전혀 읽지 않는다 — 정의만 되고 안 쓰이는 필드.

own: carla_backend.py._to_vehicle_control()이 VELOCITY_TARGET/ACCELERATION_TARGET을 어댑터 안에서 순수 P(비례)만 있는 근사로 계산한다(err * 0.5 식, 적분/미분 항 없음, ponytail: 주석 "capability matrix 확정 전 임시"). metadrive_backend.py._to_action()도 동일 P-only 패턴을 독립적으로 중복 구현한다(조향 부호가 달라 tf.steering_rad_to_native 재사용 못 함, 종방향 게인 0.5는 CARLA 쪽과 같은 값을 복붙).

avva-platform: ActuationRealizer.realize()는 control mode·actor 종류에 따라 갈린다 — VELOCITY_TARGET일 때만 진짜 PID(_pid()가 kp*error + ki*integral + kd*derivative 전항 계산)이고, ACCEL_TARGET은 PID가 아니라 accel * gain 단순 곱셈(적분/미분 없는 순수 feedforward)이다. 횡방향(조향)도 actor별로 다르다 — NPC는 목표 heading(또는 경로점 atan2)에 lateral_gains[0] P 게인을 곱한 뒤 _rate_limit()을 거치지만, Ego는 control.steering_tire_angle_rad를 게인 없이 그대로 _rate_limit()에 넣는다 — Ego 조향엔 P 매핑 자체가 없다.

종방향만 놓고 비교하면 avva-platform(VELOCITY_TARGET 기준 PID, 적분 windup 포함)이 own(순수 P, 적분 없음)보다 더 정교한 제어기를 쓰고 있다 — 다만 이건 VELOCITY_TARGET·NPC 조향에 한정된 조건부 우위다. own은 이런 모드 분기 없이 P-only 하나로 전부 처리하므로, 비교 가능한 구간(속도 target·NPC 조향)에서 avva가 더 정교하다는 결론 자체는 유효하다.

own의 P-only 컨트롤러는 own 코드 자체가 ponytail: 주석으로 "capability matrix 확정 전 임시"라고 이미 표시해뒀다.

A. own 유지 — 순수 P

지금 구현 그대로.

근거: 구현 단순, 지금까지 테스트에서 문제 없었음.

단점: 적분항이 없어 정상상태 오차가 남는다 — 저속/저가속 구간에서 목표값에 정확히 도달 못 할 수 있다.

B. avva 스타일 PID로 업그레이드(종방향만)조건부 권장

적분·미분항 추가.

근거: 정상상태 오차 제거. own 코드 스스로 이미 "확정 전 임시"라고 표시해 개선 대상으로 지정해둠.

단점: 게인(Ki, Kd) 튜닝이 추가로 필요 — 잘못 튜닝하면 오버슈트·진동 위험, 검증 비용 증가.

→ capability matrix 확정 시점에 B로. own 코드가 이미 그 시점을 트리거로 지정해뒀다 — 그 작업을 할 때 PID로 같이 올리는 게 자연스럽다. 지금 당장 급하진 않다. 참고로 avva-platform 쪽엔 이미 이 "capability matrix"에 해당하는 실행 코드(CapabilityDeclaration/matched_subset_capabilities, metadrive_probe.py)가 있다 — 다만 MetaDrive만 동적 프로빙이고 CARLA는 정적 하드코딩(§2)이라, own이 그대로 가져다 쓰기엔 avva 쪽도 아직 backend 간 방식이 안 맞는 상태다.

actor lifecycle 정체성 매핑을 별도 계층으로 뽑았는가

avva-platform은 ActorMappingStore라는 독립 컴포넌트가 canonical actor_key(정수)와 vendor-native ref(backend_id+native_id+generation) 사이의 매핑을 전담한다. bind()는 "정확히 하나의 신규 key"만 허용하고, despawn된 key는 tombstone으로 영구 봉인(재사용 금지)한다 — 매핑 자체가 하나의 독립된 상태 기계다.

이 상태 기계의 실체는 avva_contracts/actor.py에 정의된 ActorIdentityRegistry dataclass다 — bind()/tombstone()/snapshot() 전부 이 타입의 새 인스턴스를 만들어 반환한다. registry_epoch(변경마다 증가)와 registry_digest(내용 해시) 필드가 있어서, 매핑 상태 자체가 버전 스탬프 찍힌 불변 스냅샷으로 취급된다 — "정체성 매핑을 1급 개념으로 승격"이라는 아래 결론의 가장 직접적인 근거다.

own은 actor_id: str을 생성 시점부터 백엔드까지 그대로 들고 다닌다(spawn_actor(actor_id, spec)) — canonical id와 native id를 구분하는 계층이 없다. CARLA 어댑터 내부에 self._actors: dict[str, carla.Actor]라는 로컬 매핑은 있지만, 이건 "avva-sim 레벨의 공유 서비스"가 아니라 그 백엔드 클래스 하나의 사적인 내부 상태다.

원리 차이: avva-platform은 "정체성 매핑을 시스템 전체가 공유하는 1급 개념으로 승격"하고, own은 "정체성은 각 백엔드가 알아서 관리하는 구현 디테일"로 둔다. 전자는 여러 backend나 컴포넌트가 같은 actor_key로 같은 대상을 가리킨다는 걸 시스템 차원에서 보장하고 ID reuse 버그를 구조적으로 막지만 매핑 계층 자체의 복잡도(bind/tombstone/epoch)가 늘어난다. 후자는 훨씬 단순하지만 "같은 actor_id가 다른 백엔드 인스턴스에서 다른 네이티브 객체를 가리킬 수 있다"는 걸 막는 장치가 없다(지금은 백엔드가 하나뿐이라 문제가 안 드러날 뿐이다).

이 원칙은 "누가 spawn을 실행하는가"에도 적용된다. _Carla0916Client.apply_lifecycle()은 spawn/despawn 요청이 하나라도 있으면 CAPABILITY_UNSUPPORTED로 무조건 거부한다 — S1 lock 문서(CARLA_ACTUAL_GATE_S1_LOCK_KO.md)가 "actor lifecycle을 CarlaBackend에 숨기지 않고 caller가 먼저 spawn·매핑한다"고 명시한 의도된 설계다. actual_carla_smoke.py가 그 실사용 예시 — 스모크 스크립트가 world.try_spawn_actor()로 직접 spawn하고 ActorMappingStore.bind()도 직접 호출한 뒤에야 그 mapping을 CarlaBackend에 넘긴다. 즉 avva-platform은 "정체성 매핑"뿐 아니라 "spawn 실행 주체"까지 backend 밖으로 빼는 방향이고, own은 spawn_actor()가 어댑터 내부에 있어 매핑과 실행이 한 곳에 뭉쳐 있다 — 이 부분은 §4 3번 항목(Different)과 같은 결의 차이다.

구현 ActorMappingStore (actor_mapping.py) · CarlaSimulatorAdapter._actors (carla_backend.py, 사적 상태) · _Carla0916Client.apply_lifecycle()/execute_actual_carla_smoke() (신규, backends/carla.py · actual_carla_smoke.py)

own의 장기 목표(여러 시뮬레이터 + 실차를 동시에 비교하는 논문)가 실현되면, 여러 백엔드가 "같은 논리적 액터"를 동시에 가리켜야 하는 상황이 실제로 생긴다.

A. own 유지 — 매핑 계층 없음조건부 권장

지금처럼 actor_id를 직접 전달.

근거: 단일 백엔드 인스턴스 실행 시 충분히 안전, 구현 단순.

단점: "같은 actor_id가 다른 백엔드 인스턴스에서 다른 걸 가리킬 수 있다"는 위험이 구조적으로 남아있다.

B. avva 스타일 ActorMappingStore 도입

canonical key ↔ native ref bijection + tombstone.

근거: 여러 백엔드가 동시에 떠 있어도 "같은 대상"이라는 걸 시스템 차원에서 보장.

단점: 지금 단일 백엔드 구조에선 오버엔지니어링 — 당장의 이득이 없다.

→ 멀티 시뮬레이터 동시 실행을 실제로 시작하는 시점을 도입 트리거로 못박고, 그 전까지는 A 유지. 지금 미리 넣어두면 그 시점에 재작업이 줄어든다는 것만 기억해두면 된다.

repo 전체를 fixed_step_ns/target_rate_hz/숫자 리터럴 기준으로 grep해서 확인했다.

avva-platform

10.1 critical/telemetry 분리 및 overflow 시 abort (async_channel.py)정책 결정됨

→ A/B를 따질 필요 없이 구현. own의 channel_registry.yaml엔 BEST_EFFORT_TELEMETRY delivery class뿐 아니라 shm_policy 블록(critical_full: wait_queue_timeout_then_abort_epoch, telemetry_full: drop_and_increment_drop_count)까지 avva의 critical→abort / telemetry→drop 정책과 거의 1:1로 이미 선언돼 있다 — 다만 둘 다 repo 전체에서 참조하는 코드가 0건이라(grep 확인) 개념만 잡혀 있고 실행은 전무하다. avva-platform의 critical/telemetry 분리 + overflow 정책 구조를 그대로 참고해 구현하면 된다.

근거: 기존 3-profile 개념 위에 얹는 거라 구현 부담 적음, 지금 규모(단일 호스트, 고정 배치)에 맞음.

단점: 배치가 바뀌면 사람이 profile을 다시 골라야 함 — 자동 감지 없음.

→ B 권장. 배치 시나리오가 자주 안 바뀌는 졸업작품 규모에서 A는 YAGNI. 2026-08-26 결정("transport-agnostic하게 만든 뒤 나중에 ROS2를 붙이지 말고 처음부터 ROS2를 기본으로 한다")과도 맞는다 — 배치에 따라 transport class를 자동 전환하는 A의 전제 자체가 이 원칙과 결이 다르다. 대신 avva-platform의 안전장치 아이디어(critical overflow 시 run abort, §10.1)는 규모와 무관하게 채용 가치 있음.

10.6 헬스/하트비트 모니터링팀 결정 없음 · 판단

own은 ComponentHeartbeat 채널이 channel_registry.yaml에 선언만 돼 있고 ros2_node.py의 publisher 목록엔 없다 — 발행 자체가 안 붙어 있음. avva-platform은 RTT·one-way latency·backpressure까지 정량적으로 측정한다.

A. avva-platform 수준 전체 이식

RTT, clock sync certificate 기반 one-way eligibility, backpressure 판정까지 한 번에 구현.

단점: 지금 own은 하트비트 발행 자체가 없는데 정량 지표부터 만드는 건 순서가 안 맞음 — clock sync certificate 같은 선행 개념도 아직 own에 없음.

B. 최소 하트비트 발행부터권장

ComponentHeartbeat를 실제로 발행하는 코드부터 ros2_node.py에 추가(존재 확인 수준).

근거: 이미 yaml에 선언까지 해놓고 발행이 없는 게 제일 시급한 구멍 — 정량화는 그 다음 단계 문제.

→ B 먼저. 없는 것부터 채우는 게 우선이고, avva-platform 수준 정량 모니터링은 그 위에 나중에 얹을 수 있음.

own이 이미 앞선 지점 — 선택지 없음, 유지 권장

avva-platform 개발이 시작된 지 시간이 지나면서, own에는 반영됐지만 avva 스냅샷엔 아직 없는 것들이다.

① 수신자 scope 검증

own의 gate.py._check_run()은 메시지 안의 sim_id 값이 실제 자기 것과 같은지까지 검사한다. avva-platform의 identity.py(validate_identity_envelope)와 approval.py(ReadinessApprovalGate)는 포맷·범위·run_id 대조만 하고 "이 메시지를 보낸 게 실제로 등록된 그 컴포넌트 인스턴스가 맞는가"는 어디서도 확인하지 않는다. 코드 주석은 이 책임을 "message_type을 가진 transport 경계"로 미루는데, 실제 transport 코드(ControlStatusChannel, DirectDataPlaneEndpoint, AvvaSimulatorNode)에도 구현이 없다.

구현 gate.py._check_run() (own) · identity.py/approval.py (avva-platform, 해당 검증 없음)

② producer_instance_id / 재시작 감지

own은 컴포넌트 프로세스 생명주기 동안 producer_instance_id를 고정하고 event_seq를 계속 단조 증가시켜, Core가 "같은 프로세스의 연속 메시지"와 "재시작 후 새 인스턴스"를 구분할 수 있게 한다. avva-platform 전체 repo(모든 packages/)를 producer_instance_id/SEQUENCE_ANOMALY/instance_id 키워드로 검색한 결과 단 한 곳에도 없다. RunLock.amendment_id가 있긴 하지만 이건 run 단위 재승인 구분이지 컴포넌트 프로세스 재시작 구분이 아니라 다른 문제를 푼다.

구현 component.py.SimBackendComponent.__init__ (own) · avva-platform 전체에 대응 개념 없음

권장 — 둘 다 그대로 유지. avva-platform 쪽으로 되돌릴 이유가 없고, 오히려 이 두 패턴(수신자 scope 검증, 프로세스 인스턴스 식별)을 재사용 가능한 공용 유틸로 뽑아서 Traffic/Ego 등 다른 컴포넌트에도 같은 방어를 적용하는 걸 팀에 제안할 가치가 있음.

avva-platform이 "조립 계층이 통째로 없음"(§4)이었다면, own은 그 조립 계층을 실제로 짜뒀고 동작을 확인했다.

그런데 own에도 같은 패턴의 구멍이 하나 있음 — control channel이 ROS에 안 이어짐

SimBackendComponent(component.py) — RunManifest/RunControlCommand를 다루는 공식 진입점 — 가 ROS 쪽에 전혀 연결돼 있지 않다.

  • ros2_node.py를 RunManifest/RunControlCommand/run/manifest/run/control로 검색하면 0건 — SimulationLayerNode는 frame data path(NpcControlBatch/AdvanceFrame/FrameCompleteAck/EgoControlCommand)만 ROS 구독하고, RunManifest/RunControlCommand용 구독은 아예 없다.
  • SimBackendComponent( 생성 호출은 자기 자신의 테스트 파일(test_component.py) 안에서만 존재 — 실제 데모/런처 어디서도 안 씀.
  • demo_ros2_lifecycle.py조차 SimBackendComponent를 거치지 않고 SimulationLayerNode를 직접 씀.
  • component.py 자체 docstring: "외부(transport binding)는 이 6개 메서드만 호출한다. Bootstrap Transport 준비는 이 클래스 밖(호출자) 책임" — avva-platform의 _composition_provider("외부 provider가 주입해야 함")와 구조적으로 동일한 패턴.

결론 — avva-platform의 AvvaSimulatorNode가 on_run_manifest/on_run_control이 없는 것과, own의 ros2_node.py가 RunManifest/RunControlCommand ROS 구독이 없는 것은 정확히 같은 종류의 미완성이다. avva-platform만의 약점이 아니라 두 구현 모두 "control channel을 실제 transport에 잇는 마지막 단계"를 아직 안 한 것 — eCAL 전환 작업이나 own 코드 통합 작업 때 own도 같이 채워야 한다.
